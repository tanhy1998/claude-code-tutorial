Lesson 6 · From blocking to checking

Hooks II: check every TMDL write

A PreToolUse hook says "not now". A PostToolUse hook looks at what a tool just did, and if it's wrong, tells Claude to fix it.

~40 minHands-on: terminal + editor (Desktop stays closed)Primary source: Hooks reference: PostToolUse
Why this, now Microsoft says PBIP files you edit outside Desktop should be saved using UTF-8 without BOM encoding, and that Power BI Desktop uses CRLF as end-of-line.PBIP overview: Considerations and limitations (Microsoft Learn). Note the difference: the encoding is a rule, while CRLF is there to avoid problems in your diffs. Your CLAUDE.md already says so, but that's context: Claude chooses to follow it. And as you'll see in Part B, three of Claude's own write paths produce something else. Today the check moves into code that runs after every write.

Your win today: a hand-written, committed PostToolUse hook. After every Edit, Write, or shell command, it checks each changed .tmdl file. If one is UTF-16, ANSI, has a BOM, or has LF line endings, Claude gets told exactly what's wrong and fixes it in the same turn.

Warm-up

Answer from memory.

W1. Your project settings.json denies Edit(.pbi/**). Your settings.local.json allows it. Claude tries to edit .pbi\editorSettings.json. What happens?

Deny, then ask, then allow, across every scope. You proved this in Lesson 3 step 7. Scope precedence only matters between settings that don't conflict this way.

W2. A PreToolUse hook script crashes and exits 1. onFailure isn't set. What happens to the Edit?

Only exit 2 blocks. A crash fails open unless you set "onFailure": "block". Today that matters in a new way: PostToolUse exit codes work differently (Part A).

W3. You want a hook to see every Edit and every shell command on Windows. Which matcher?

Bare tool names, case-sensitive, and on Windows shell commands go through PowerShell. Edit(…) is permission-rule syntax: it belongs in if or in permissions, never in matcher. The full list of names is in the Tools reference.

Part A: After the tool, not before

Claude decides: Write(Scratch.tmdl)
  │
  ├─ PreToolUse hooks     Lesson 5: can block
  ├─ permission rules, mode
  ├─ the tool runs        ← the file is on disk now
  │
  └─ PostToolUse hooks    today: can't block, can't undo
        exit 2 → your stderr goes to Claude, next to the tool result
        exit 0 → nothing reaches Claude

PostToolUse runs immediately after a tool completes successfully. It uses the same matchers as PreToolUse.Hooks reference: PostToolUse. If the tool fails, PostToolUse doesn't run. PostToolUseFailure does instead. The exit-code table changes meaning:

ExitPreToolUse (Lesson 5)PostToolUse (today)
0Carry onCarry on. Claude never sees your stderr
2Blocks the callShows stderr to Claude; the tool already ran
otherNon-blocking errorNon-blocking error: a notice for you, nothing for Claude

So the docs' advice is: To surface a warning to Claude from a PostToolUse… hook, exit 2 instead so Claude sees the stderr even though the tool already ran.Exit code output and the exit 2 table per event. There's also a JSON form ("decision": "block" + "reason"), but despite the name it doesn't block anything. It adds the reason next to the tool result. Your hook is a reviewer, not a gate: it can't stop a bad write, but it makes sure Claude finds out and fixes it before moving on.

Part B: What Claude's write paths actually produce

I tested each one on your machine (Claude Code v2.1.303, Windows PowerShell 5.1), writing é so encoding bugs show up:

How the file was writtenBytes on diskOK for PBIP?
Edit on an existing CRLF fileKeeps CRLF. Keeps a BOM if the file already had one✅ (won't clean up an existing BOM)
Write, new fileUTF-8, no BOM, LF line endings⚠️ LF
Set-Content / Add-ContentANSI: é becomes the single byte E9, which isn't valid UTF-8❌
Out-File / >UTF-16 LE with BOM FF FE❌
[IO.File]::WriteAllText(path, text)UTF-8, no BOM, line endings exactly as in text✅

The PowerShell rows are documented Windows PowerShell 5.1 defaults, not a Claude quirk.about_Character_Encoding. PowerShell 7 defaults to UTF-8 without BOM, but your machine only has 5.1, and so does a typical teammate's. With pure-ASCII content, Set-Content happens to look fine, which is why this kind of bug slips through until someone types Café.

Part C: Which files to check?

Edit and Write tell your hook the file_path. A PowerShell command only gives its text (Lesson 5). And the docs warn that Claude Code doesn't run a PostToolUse hook matching Edit|Write when a Bash command… rewrites the same file. Their suggestion: Your hook can then discover what changed itself, for example by running git status --porcelain.Hooks reference: PostToolUse, matcher notes. --untracked-files=all also lists new files inside new folders. Not tested: the Monitor tool also runs commands and isn't in your matcher. A write from it would be caught at the next matched call, because git still lists the file.

So the hook ignores its stdin and asks git: which .tmdl files differ from the last commit? Then it checks those files' bytes on disk. Check the disk, not git's copy: with autocrlf, git stores your TMDL with LF and turns it back into CRLF on checkout. I checked, and git show HEAD:…Stores.tmdl has no CR bytes at all.

ProblemHow the script spots it
UTF-16First two bytes are FF FE
BOMFirst three bytes are EF BB BF
ANSIA strict UTF-8 decoder throws
LFRegex (?<!\r)\n: a newline with no CR before it

    Fill in the four (write …) parts. Plain ASCII only, so no curly quotes or em dashes.

    lab\.claude\hooks\check-tmdl.ps1# PostToolUse check: every changed .tmdl must be UTF-8 without BOM, with CRLF.
$ErrorActionPreference = "Stop"
Set-Location $env:CLAUDE_PROJECT_DIR

# Shell commands don't name their files, so ask git what changed.
$changed = (write: git status, porcelain, all untracked files, only '*.tmdl')
$strict  = New-Object System.Text.UTF8Encoding($false, $true)   # no BOM, throw on bad bytes

$problems = foreach ($line in $changed) {
    $f = $line.Substring(3).Trim('"')
    if (-not (Test-Path -LiteralPath $f)) { continue }          # deleted files
    $b = [IO.File]::ReadAllBytes((Resolve-Path -LiteralPath $f))
    if ($b.Length -ge 2 -and $b[0] -eq 0xFF -and $b[1] -eq 0xFE) { "$f is UTF-16"; continue }
    (write: if the first three bytes are EF BB BF, output "$f starts with a BOM")
    try { $text = $strict.GetString($b) } catch { "$f is not valid UTF-8 (ANSI?)"; continue }
    (write: if $text has a newline with no CR before it, output "$f has LF line endings, not CRLF")
}
if (-not $problems) { exit 0 }

(write: one message to stderr: the problems, one per line, and how to fix them; then the exit that reaches Claude)

    Inside foreach, any bare string is output, and $problems collects it. That's why the checks are just strings.

    Write your version first, then compare. Hint: the stderr message is the only thing Claude learns, so give it the fix as well as the problem.

    $changed = git -c core.quotepath=off status --porcelain --untracked-files=all -- '*.tmdl'

Part E: Retrieval practice

Scroll up only after you've answered.

1. Your PostToolUse hook exits 2 after an Out-File wrote a UTF-16 TMDL file. What happens to that file?

Shows stderr to Claude; the tool already ran. PostToolUse is a reviewer, not a gate. Nothing is undone unless something writes the file again.

2. Why does the script ask git status instead of reading tool_input.file_path?

Edit and Write do pass file_path, in PostToolUse too. A shell command doesn't, and it's the shell that writes ANSI and UTF-16. Asking git covers every write path with one method.

3. In Windows PowerShell 5.1, Claude runs Set-Content _Measure.tmdl $text, and $text contains Café. What lands on disk?

Set-Content and Add-Content write ANSI, while Out-File and > write UTF-16. Only [IO.File]::WriteAllText gives UTF-8 without BOM by default.

4. Which of these does Microsoft Learn state as a rule for externally edited PBIP files, rather than diff hygiene?

PBIP files should be saved using UTF-8 without BOM encoding. CRLF is because Power BI Desktop uses CRLF, and autocrlf is how Learn suggests you avoid problems in your diffs. Your hook enforces both, but only one is the hard rule.

5. Your PostToolUse check finds a problem but exits 1 instead of 2. What does Claude see?

Any other exit code is a non-blocking error: you get a notice in the transcript, and Claude carries on unaware. Exit 2 is the only way your stderr reaches Claude.

Write it out: the whole "hooks" object as it is now, with both events, from memory. Then, in one sentence: why does the PreToolUse hook have onFailure but the PostToolUse hook doesn't?

"hooks": {
  "PreToolUse": [
    { "matcher": "Edit|Write|PowerShell|Bash",
      "hooks": [ { "type": "command", "command": "powershell.exe",
                   "args": ["-NoProfile", "-ExecutionPolicy", "Bypass", "-File",
                            "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-unapplied.ps1"],
                   "onFailure": "block" } ] } ],
  "PostToolUse": [
    { "matcher": "Edit|Write|PowerShell|Bash",
      "hooks": [ { "type": "command", "command": "powershell.exe",
                   "args": ["-NoProfile", "-ExecutionPolicy", "Bypass", "-File",
                            "${CLAUDE_PROJECT_DIR}/.claude/hooks/check-tmdl.ps1"] } ] } ]
}

onFailure: "block" turns a crashed guard into a block. PostToolUse can't block, because the tool has already run, so there's nothing for it to do.
