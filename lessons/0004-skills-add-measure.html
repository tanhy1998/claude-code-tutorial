Lesson 4 · From rules to procedures

Skills: turn "add a measure properly" into /add-measure

CLAUDE.md and rules say what must be true. A skill says how to do a job, step by step, and loads only when that job comes up.

~45 minHands-on: terminal + editor + Power BI DesktopPrimary source: Extend Claude with skills
Why this, now Adding measures is the most common change you make to a model. Doing it properly takes the same steps every time: check for pending Desktop changes, check the measure doesn't already exist, check the columns exist, pick the team format string, give it a fresh lineageTag, then Apply in Desktop. Today you have to type all of that into the prompt, or hope Claude remembers it. A skill packs the steps into one command your team gets from git, and it costs almost no context until someone uses it.

Your win today: a hand-written, committed /add-measure skill. You'll use it to add Total Cost to the Contoso model and see it applied in Desktop. You'll also watch it stop when Desktop has unapplied changes, and catch a duplicate measure.

W1. Project settings have an ask rule for Edit(**/*.Report/definition/report.json). Your local file allows Edit(**/definition/report.json). You're in auto mode, and Claude edits that file. What happens?

Deny, then ask, then allow. The first match wins, whichever file it comes from. Scope precedence only decides single values such as model.

W2. Which deny rule blocks localSettings.json in every .pbi folder, at any depth?

A pattern with a / between segments is anchored at the launch folder. **/ removes the anchor. A leading / anchors to the project root, so it's still one location.

Part A: What a skill is, and when it loads

A skill is a folder with a SKILL.md file in it. It has frontmatter (like your rules), then markdown instructions. The thing that sets it apart is when it loads. By default, the description [is] always in context, [and the] full skill loads when invoked.Control who invokes a skill. Old .claude/commands/*.md files still work and make the same /name, but the docs recommend skills for new work, because skills add supporting files and invocation control. Claude reads the one-line description in every session. The body only arrives when you type /add-measure, or when Claude decides your request matches the description.

When two skills have the same name: enterprise over personal, and personal over project. Compare the same pair of folders in settings: there, the project's .claude\settings.json beats your user ~\.claude\settings.json. For skills it's reversed, and your personal folder beats the project. (Settings also has a local file, which outranks project, but skills have no local level, so it isn't part of this comparison.) A personal add-measure left over from an experiment would hide the team's. Plugin skills have a namespace, so they never clash.Where skills live. Claude Code watches skill folders and picks up edits without a restart. One exception: if .claude\skills\ didn't exist when the session started, run /reload-skills.

Part B: Anatomy of SKILL.md

.claude\skills\add-measure\SKILL.md---
name: add-measure                        ← the /command. Defaults to the folder name
description: Adds one DAX measure … Use when I ask to add a measure.
                                         ← always in context; Claude matches on it
argument-hint: "[name and what it calculates]"   ← grey hint after /add-measure
shell: powershell                        ← run !`…` lines in PowerShell, not Bash
allowed-tools:                           ← pre-approved for the turn that invokes it
  - PowerShell(New-Guid)
---

- Unapplied changes: !`Test-Path Contoso.SemanticModel/.pbi/unappliedChanges.json`
                       ↑ runs BEFORE Claude reads this; the output replaces it
## Request
$ARGUMENTS                               ← whatever you typed after /add-measure
## Steps
1. …                                     ← the procedure

Three mechanisms you'll use

  1. Arguments. $ARGUMENTS is everything you typed. $0, $1… are single words, counting from 0. Quoting groups words: "Total Cost" is one argument. Trap: any $ followed by a digit is a placeholder, so "over $1 million" in your instructions turns into the second argument. Write \$1. (I tested this on v2.1.302. \$#,0.00 format strings are left alone.)Available string substitutions.
  2. Dynamic context: !`command`. Claude Code runs the command before Claude sees the skill and pastes in the output. Claude never runs it and never decides whether to run it. It just reads the result. That makes it a good fit for facts that change, such as "are there pending changes right now?" or "which measures exist?". Two rules: a command that fails aborts the entire skill invocation, and commands go through permission checks.Inject dynamic context. With shell: powershell, the commands run in PowerShell, so a teammate without Git Bash can still use the skill.
  3. Supporting files. Other files in the skill folder load only when SKILL.md tells Claude to read them. Put lookup material there, such as your team's format strings. Claude only spends context on them when it needs them.Add supporting files. The docs suggest keeping SKILL.md under 500 lines.
What I found testing on v2.1.302 (manual mode)

In auto mode, all the !`…` lines ran. In manual mode, a teammate's likely default, Test-Path and Select-String ran without approval because they're read-only, but New-Guid didn't. The whole skill aborted with no message: the result was empty. The reason only appeared in the debug log: Shell command permission check failed for command in /probe: New-Guid. Listing it under allowed-tools fixed it.

Two more limits I hit: wildcards such as *.SemanticModel/… were refused even with allowed-tools (Glob patterns in paths cannot be statically validated), and so were .NET calls such as [guid]::NewGuid() and script blocks (| ForEach-Object { … }). Use literal paths and plain cmdlets.

Use disable-model-invocation: true for jobs where you choose the moment, such as a future /commit-model or a deploy. /add-measure is the opposite: you want add a measure for total cost to trigger it without typing the slash. Its edits are still covered by your rules and permissions, and they're easy to review in git.allowed-tools pre-approves tools. It does not restrict which tools are available, and the grant ends when you send your next message. To block a skill entirely, use a permission rule: Skill(add-measure *) in deny.

Lifecycle: once invoked, the skill's text stays there across later turns, and Claude Code does not re-read the skill file. Edit SKILL.md mid-task, and Claude keeps following the old copy until you invoke it again. So write steps as standing instructions (after every edit…), and put the most important ones first.Skill content lifecycle. After auto-compaction, Claude Code re-attaches the first 5,000 tokens of each recently used skill.

Part D: Do it

  1. Prep (3 min). In VS Code, open settings JSON (Ctrl+Shift+P → Preferences: Open User Settings (JSON)) and add:

    "workbench.editorAssociations": { "*.md": "default" }

    VS Code now opens .md files as plain text. Notepad is also fine. Then delete the CANARY line from lab\.claude\rules\tmdl.md.

  2. Create the folder before you start Claude. In PowerShell, in lab\:

    mkdir .claude\skills\add-measure
code .claude\skills\add-measure\SKILL.md

    If a Claude session is already open, run /reload-skills in it. .claude\skills\ didn't exist when that session started.

  3. Write SKILL.md by hand. Start from this skeleton and fill in the three (write …) parts yourself. For the measures line, use Select-String with -Path pointing at _Measure.tmdl and a -Pattern that matches measure lines and displayFolder lines. Keep it to one plain command, with no pipe. Each !`…` command must stay on one line in the file, even where this page wraps it.

    lab\.claude\skills\add-measure\SKILL.md---
name: add-measure
description: (write this: what it does, then "Use when …")
argument-hint: "[measure name and what it calculates]"
shell: powershell
allowed-tools:
  - PowerShell(New-Guid)
---

Part E: Retrieval practice

Scroll up only after you've answered.

1. You have an old ~\.claude\skills\add-measure\ from an experiment, and the team's .claude\skills\add-measure\. You type /add-measure. Which runs?

Enterprise, then personal, then project: the docs' own example is /deploy runs the personal one. Settings go the other way for the same two folders: the project's settings.json beats your user ~\.claude\settings.json. If a teammate says the skill behaves oddly, ask whether they have a personal copy with the same name.

2. You add disable-model-invocation: true. What changes?

That's why step 9's "What skills are available?" didn't list it. Claude can't pick a skill whose description it never sees. user-invocable: false is the reverse: Claude only.

3. When does !`New-Guid` in SKILL.md run?

It's preprocessing. Claude Code runs it at invocation, and Claude only ever sees the result. Each invocation runs it again, so every measure gets a fresh GUID.

4. Your SKILL.md says Flag measures that could exceed $1 million. You run /add-measure Total Cost. What does Claude read?

Unquoted, Total Cost is two arguments: $0 = Total, $1 = Cost. Write \$1 for a literal dollar sign. \$#,0.00 survived my test, but don't rely on that pattern near digits.

5. What does allowed-tools: [PowerShell(New-Guid)] do?

It's a temporary allow, and it clears on your next message. To remove tools while a skill runs, use disallowed-tools. Deny rules still win, as always.

6. A teammate in manual mode runs your skill, but allowed-tools is missing. What happens?

In my v2.1.302 test it aborted with no message, and the reason was only in the debug log. You're in auto mode, so you'd never see this yourself. That's why the team version needs allowed-tools, and why Lesson 10's CI checks matter.

7. Every measure needs a displayFolder: General, Sales, or Product. Where should that line live?

It's a convention, not a step. It should also apply when Claude renames or moves a measure without the skill. Permission rules match tools and paths, not TMDL content. Checking content automatically is a hook's job (Lesson 6).

8. You invoked /add-measure, then fixed a step in SKILL.md. Your next message says "continue". Which version does Claude follow?

Watching the folder updates the skill listing and future invocations. The copy already in the conversation stays as it is, because Claude Code does not re-read the skill file on later turns.

Write it out: frontmatter for a /document-model skill that only you can invoke, shows [table name] as a hint, and runs its !`…` lines in PowerShell. Then say in one sentence why the add-measure steps belong in a skill and not in CLAUDE.md.

---
name: document-model
description: Writes a markdown summary of one table's measures and columns. Use when I ask to document the model.
argument-hint: "[table name]"
disable-model-invocation: true
shell: powershell
---

CLAUDE.md is loaded in full every session, even when you're editing a visual. A skill costs only its description until someone needs it, and then the steps arrive together, in order.
