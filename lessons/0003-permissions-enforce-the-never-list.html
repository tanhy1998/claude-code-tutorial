Warm-up

Answer from memory.

W1. Your pbir.md now starts with \--- instead of ---. When does it load?

With no valid --- opening line there's no frontmatter, so there's no paths. A rule without paths loads at launch. It's the same silent failure as broken YAML, and you can spot it the same way: it's listed under Memory files in /context before any file has been opened.

W2. Which of these does Claude Code enforce no matter what Claude decides?

CLAUDE.md, rules, and memory are all context: text Claude chooses to follow. Permission rules are enforcement. The harness checks every tool call against them before it runs.

Part A: Where settings live

Settings are JSON files. Four can affect you, and each has a different reach:Settings files and who they affect. On Windows, ~/.claude means %USERPROFILE%\.claude. Claude Code reads the shared project file from the directory you launch in. That's why you start your lab sessions in lab\.

ScopeFileReachesIn your PBIP setup
Managedmanaged-settings.json, MDM, or the claude.ai consoleEveryone your org deploys it toYour company's IT, later. /status shows whether one applies.
Project local.claude\settings.local.jsonYou, in this repo onlyPersonal shortcuts. If you create it by hand, gitignore it yourself.
Shared project.claude\settings.jsonEveryone who clones the repoThe team's PBIP guardrails. Today's file.
User~\.claude\settings.jsonYou, in every projectYour preferences everywhere

For a single value, such as model, the highest level wins: managed, then command line, then local, then project, then user. Lists like permissions.deny merge, so every file adds entries. Then one rule overrides precedence: if user settings allow a permission and project settings deny it, the deny rule blocks it, and the reverse is also true. A deny from any scope wins.Lists merge instead of overriding · Permissions: settings precedence.

Part B: How a permission rule works

1. Three lists, checked in a fixed order

.claude\settings.json{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [ … ],   ← runs without asking
    "ask":   [ … ],   ← always asks you
    "deny":  [ … ]    ← refused
  }
}

Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order. As a result, an allow rule can't carve an exception out of a deny rule.Manage permissions. The $schema line gives you autocomplete and red squiggles in VS Code. The file is strict JSON: a trailing comma or a // comment is a Settings Error at startup.

2. A rule is Tool(specifier). For files, use only Read and Edit

  • Edit(path) covers every built-in tool that changes files.
  • A Read(path) deny also blocks Edit and Write on that path. In my test it also hid the file from Glob: Claude couldn't even see it in a file listing.
  • Write(…) and Glob(…) path rules are accepted but never consulted, and you get a startup warning.Read and Edit. Claude Code ignores .claudeignore. Put those entries in Read deny rules instead.

3. Paths use gitignore syntax. The shape decides the depth

This is the part that bites. Read each row slowly:

Every row is quoted from or tested against the Read and Edit section. I ran the .pbi rules against a copy of your folder layout on v2.1.302.

4. Modes set the baseline, and rules sit on top

Mode (status bar)Runs without asking
default · ⏸ manual mode onReads only
acceptEdits · ⏵⏵ accept edits onReads, edits, mkdir/mv/cp… in your folder
plan · ⏸ plan mode onReads. No edits until you approve a plan.
auto · ⏵⏵ auto mode onEverything, after a classifier checks shell and network actions. Your default.

Shift+Tab cycles modes. Two facts matter for a team repo. Ask rules still prompt in auto mode: Tools matched by an explicit ask rule are never auto-approved. And a project file can't switch on auto or bypassPermissions for your teammates. Set to bypassPermissions there, the session starts in Manual mode.Available modes · Which mode a session starts in. The dontAsk and bypassPermissions modes are for CI and containers (Lesson 10).

What a deny rule doesn't cover

Read/Edit denies cover Claude's file tools, Bash file commands Claude Code recognizes (cat, head, sed, tee…), and redirects like > file. In my test on v2.1.302, PowerShell's Get-Content was blocked too, although the docs only promise this for Bash. They don't cover a Python or Node script that opens files itself, or grep -r run over a folder. That matters once cache.abf holds company data. A deny rule is a strong default, not a security boundary. Hooks (Lesson 5) and sandboxing add more layers.

Windows trap: any Bash(…) deny rule silently turns off the PowerShell tool. Pair it with the matching PowerShell(…) rule (tools reference). Today's rules are all Read/Edit, so this doesn't affect you yet.

Part E: Retrieval practice

Scroll up only after you've answered.

1. Project settings.json denies Edit(diagramLayout.json). Your settings.local.json allows Edit(**/diagramLayout.json). Claude tries the edit. What happens?

Lists merge across files, and then deny, ask, allow are checked in that order. Scope precedence decides single values like model. It never lets an allow beat a deny.

2. You're in auto mode, and the settings have an ask rule for Edit(**/*.Report/definition/report.json). Claude edits that file. What happens?

An explicit ask rule is on the list of actions that no mode auto-approves. That makes ask the right tool for "Claude may do this, but I always want to see it."

3. Why Edit(**/*.Report/report.json) rather than just Edit(report.json)?

Gitignore semantics: a bare file name matches at any depth. That would block the PBIR definition/report.json too, and the deny would win over your ask rule.

4. Why not simply deny Read(**/.pbi/**) to protect the cache?

A Read deny hides matching files from Glob too. Your CLAUDE.md asks Claude to stop if .pbi/unappliedChanges.json exists, so Claude must be able to see it. Deny reads on the two sensitive files and deny edits on the whole folder.

5. You deny Read(.pbi/localSettings.json). Is Contoso.SemanticModel/.pbi/localSettings.json blocked?

A pattern with a / between segments is anchored at the starting folder, so it only matches lab/.pbi/localSettings.json, which doesn't exist. Add **/, or use the bare file name.

6. Which of these can a Read(**/.pbi/cache.abf) deny rule not stop?

Permission rules match tool calls and the file commands Claude Code recognizes. A subprocess that opens files itself is invisible to them. For that you need a sandbox or a hook that inspects the command.

7. A teammate commits "defaultMode": "bypassPermissions" in the project settings.json. You start Claude there. Which mode are you in?

auto and bypassPermissions don't take effect from project or local settings, so a cloned repo can't put you in either mode. Set to bypassPermissions there, the session starts in Manual.

8. You want Claude to run git add without asking, for you only, in this repo. Where does the rule go?

Local scope is you, in this project. The CLAUDE.md and rule-file options are context: they can't grant a permission.

Write it out: a permissions block that (1) stops Claude reading the model cache in any model folder, (2) stops every edit inside any .pbi folder, and (3) always asks before editing PBIR definition/report.json. Then say in one sentence why the CLAUDE.md line is still worth keeping.

"permissions": {
  "deny": [
    "Read(**/.pbi/cache.abf)",
    "Edit(.pbi/**)"
  ],
  "ask": [
    "Edit(**/*.Report/definition/report.json)"
  ]

The rule enforces and the CLAUDE.md line explains. Without the why, Claude hits the block and may look for another way to do the task.
