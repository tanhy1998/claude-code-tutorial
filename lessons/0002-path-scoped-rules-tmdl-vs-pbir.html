Lesson 2 · Memory, scoped

Rules: different instructions for TMDL and PBIR

Claude gets your measure conventions only when it touches the model, and your report rules only when it touches the report.

~35 minHands-on: terminal + Power BI DesktopPrimary source: Organize rules with .claude/rules/
Why this, now Look at the Team conventions you wrote in lab\CLAUDE.md: _Measure, display folders, measure names. Every line is about TMDL. Right now Claude loads them in every session, including sessions where it only moves a visual. As your team's repo grows to several models and reports, CLAUDE.md fills up with instructions that are irrelevant most of the time. The docs name the fix: If an entry … only matters for one part of the codebase, move it to a … path-scoped rule (memory docs).

Your win today: two hand-written rule files, tmdl.md and pbir.md. You'll see each one load only when Claude opens a matching file. Your measure-naming convention will still catch a bad name, even though it no longer lives in CLAUDE.md.

Warm-up: from last time

Answer from memory. Spacing these out is what moves them into long-term memory.

W1. Your repo has both AGENTS.md and CLAUDE.md, and CLAUDE.md has no @AGENTS.md line. What does Claude load by default?

By default it's one or the other: a CLAUDE.md or CLAUDE.local.md in your working directory or above it means AGENTS.md isn't read. To load both, put @AGENTS.md in CLAUDE.md, or set /config → Project instructions → claude-md-and-agents-md (docs).

W2. A teammate says, "We wrote NEVER edit diagramLayout.json in CLAUDE.md, so we're safe." What's the flaw?

CLAUDE.md is context, not enforcement. That's true of rules too: everything in this lesson is still context. The hard block comes in Lesson 5.

Part A: What a rule is

1. A rule is a markdown file in .claude/rules/

You put one topic per file, with a descriptive name. Claude Code finds every .md file in that folder, including files in subfolders.Set up rules. There's also a personal level, ~/.claude/rules/, which applies to every project on your machine. User rules load before project rules, and neither overrides the other. On its own, a rule is no different from CLAUDE.md: Rules without paths frontmatter are loaded at launch with the same priority as .claude/CLAUDE.md.

2. paths: is what makes a rule load on demand

Add YAML frontmatter with a paths list, and the rule loads when Claude uses the Read, Write, or Edit tool on a matching file. It also loads when Claude views a matching file with a single-file Bash read such as cat or head.Path-specific rules. paths is the only frontmatter field that rules read. Any other field is silently ignored, and the frontmatter is removed before the rule reaches Claude. Until then, the rule costs no context.

.claude\rules\tmdl.md---
paths:
  - "**/*.tmdl"
---

# TMDL rules
- All measures live in the `_Measure` table …

3. Patterns are globs, relative to the project root

PatternMatches in your lab
**/*.tmdlEvery TMDL file at any depth: model.tmdl, tables/_Measure.tmdl, …
*.tmdlTMDL files in the project root only. There are none, so this rule would never load.
**/*.Report/definition/**/*.jsonPBIR JSON in any report folder, now and after you add Finance.Report
**/*.{tmdl,pbism}Brace expansion: two patterns in one
Two silent failures

Quote every pattern. In YAML, a value that starts with * is an alias, so an unquoted - **/*.tmdl is a syntax error. That matters because of the second failure:

Broken YAML doesn't fail loudly. If the YAML between the markers doesn't parse, Claude Code ignores the frontmatter and loads the rule as if it had no paths. The rule still works, but it loads in every session, so you never notice it's no longer on demand. Run claude --debug to see the parse error (frontmatter reference).

4. After /compact, path rules wait for the next match

The project-root CLAUDE.md is re-read from disk after compaction. Path-scoped rules are not. They load again on demand, so if Claude seems to have forgotten your TMDL conventions after /compact, it's because it hasn't opened a .tmdl file since.Troubleshoot memory issues, the section titled "Instructions seem lost after /compact".

5. Where each instruction goes

HomeLoadsUse it for (in PBIP)
Project CLAUDE.mdEvery session, at launchThings true for every file: never-edit list, UTF-8/CRLF, Save → Apply workflow
Rule, no pathsEvery session, at launchSame as CLAUDE.md, split into topic files. Organises; doesn't save context.
Rule with pathsWhen Claude reads, writes, or edits a matching fileTMDL conventions; PBIR rules. Matches by file type, across every model and report folder.
Subdirectory CLAUDE.mdWhen Claude touches a file in that folderSomething specific to one folder, e.g. one model with odd rules
Skill (Lesson 4)When invoked, or when Claude judges it relevantProcedures: "add a report page", "publish to test"

The docs' note: For task-specific instructions that don't need to be in context all the time, use skills instead. Rules are for facts and constraints about a file type. Skills are for step-by-step procedures.

Part B: A bug in your CLAUDE.md

Before you split anything, fix a conflict that path-scoped rules would make worse. Your CLAUDE.md says NEVER edit … report.json. I put that line in Lesson 1, copied from Microsoft's list. But your repo has two kinds of report.json:

  • Contoso.Report\report.json (folder root) is the PBIR-Legacy format. It doesn't support external editing. Your lab doesn't have one.MS Learn: report folder. The external-editing page just says report.json and doesn't say which one. When the source is ambiguous, write the conservative rule and say why.
  • Contoso.Report\definition\report.json is the PBIR report metadata (report-level filters, theme). It's a required, schema-documented PBIR file.

Make the line say exactly which file it means. Your PBIR rule will then say how to treat the other one. If two instructions contradict each other, Claude may pick one arbitrarily.

Part C: Do it

  1. Create the folder, then open a new file in your editor:

    cd $HOME\Desktop\Claude\claude-code-tutorial\lab
New-Item -ItemType Directory -Force .claude\rules
notepad .claude\rules\tmdl.md      # or: code .claude\rules\tmdl.md

  2. Write tmdl.md by hand. Cut your Team conventions out of CLAUDE.md and rewrite them here as separate, checkable lines. Below is a model; use your own words. The last two lines are TMDL syntax facts from Microsoft's TMDL docs. The canary line is temporary: it lets you see when the rule has loaded.

    lab\.claude\rules\tmdl.md---
paths:
  - "**/*.tmdl"
---

# TMDL (semantic model) rules
- All measures live in the `_Measure` table, each with a `displayFolder`
  (General, Sales, Product). Flag any measure that has none.
- Measure names are business-friendly, with units where they apply:
  `Gross Profit (%)`, `Total Sales`. Never `_Sales` or `sales_num`.
- Every measure has a `formatString`.
- Indent with tabs. Multi-line DAX sits one level deeper than the measure's properties.
- Wrap names in single quotes if they contain a space, `.`, `=`, `:` or `'`.
- CANARY (remove after Lesson 2): end every reply with "(tmdl rule)".

  3. Write pbir.md yourself. No model this time. Use the glob from Part A that covers any report folder. Turn these facts from MS Learn: PBIR format into short, checkable lines, and add a canary that says (pbir rule):

    • Every PBIR file declares a $schema URL at the top and must conform to it. An invalid schema or a missing required property is a blocking error in Desktop.
    • Page and visual folders are named after the object's name property (a 20-character ID). Renaming might break external references. Names may only contain letters, digits, _ or -, and Desktop must be restarted after a rename.
    • visual.json and bookmark files can hold data values from the model, such as filter values and slicer selections. That matters once you work with company data.
    • From Part B: decide what to say about definition/report.json.

    Write your pbir.md in the file first. Then type the frontmatter here from memory and compare it with mine.

    lab\.claude\rules\pbir.md---
paths:
  - "**/*.Report/definition/**/*.json"
---

# PBIR (report) rules
- Keep each file's `$schema` line and only use properties that schema allows.
  Invalid JSON or schema = Desktop refuses to apply the change.
- Never rename page/visual folders or their `name` property unless I ask.
  If I do: only letters, digits, `_`, `-`; remind me to restart Desktop.
- visual.json and bookmarks can contain real data values (filters, slicers).
  Don't quote them back in summaries.
- `definition/report.json` holds report-level settings: ask before editing it.
- CANARY (remove after Lesson 2): end every reply with "(pbir rule)".

    If your pattern was Contoso.Report/…, it works today but silently stops covering the next report your team adds.

  4. Fix the CLAUDE.md line from Part B so it names the root-level, PBIR-Legacy report.json specifically. Check that no TMDL conventions are left in CLAUDE.md.

  5. Predict, then check: restart Claude in lab\ and run /context. Before you look, predict whether tmdl.md and pbir.md appear under Memory files. They're path-scoped and no file has been opened yet, so they shouldn't. If one appears, its frontmatter didn't parse.

  6. Report-only test. Ask: What visuals are on Page 1, and what does each one show? Claude has to open visual.json. The reply should end with (pbir rule) and not (tmdl rule). You may also see a line in the terminal when a rule loads.

  7. Convention test. With Desktop saved, ask: Add a measure margin_pct: gross margin as a % of Total Sales, using Products[UnitCost]. The naming rule now lives only in tmdl.md. Claude should open _Measure.tmdl, which loads the rule, then object to the name margin_pct and propose something like Gross Margin (%), with a display folder and format string. The reply should end with (tmdl rule). Apply external changes in Desktop. 🎉

  8. Break it on purpose. In tmdl.md, remove the quotes around **/*.tmdl. Restart Claude and run /context. Predict first: does tmdl.md now appear at launch? Then run claude --debug and look for the parse error. It goes to the newest log file in ~\.claude\debug\, not the screen (see Lesson 3, step 1). Put the quotes back. Part D: Retrieval practice

Close Part A in your head first.

1. tmdl.md has paths: ["**/*.tmdl"]. You ask Claude to retitle the bar chart, and it opens only visual.json. Is the TMDL rule in context?

A path-scoped rule loads when Claude reads, writes, or edits a matching file (Read/Write/Edit, or a single-file cat/head). Mentioning the model in your prompt doesn't count.

2. You write paths: ["*.tmdl"], correctly quoted. What happens in the lab repo?

Patterns are relative to the project root, and * doesn't cross folders. Your TMDL lives under Contoso.SemanticModel/definition/, so you need **/.

3. Your rule's frontmatter has a YAML syntax error. What does Claude Code do?

It ignores the frontmatter and treats the rule as unscoped. The rule still works, so the mistake is easy to miss. claude --debug shows the parse error, and /context shows the rule loaded at launch.

4. Next month the repo gets a second report, Finance.Report. Which pattern covers PBIR JSON in both reports?

The *.Report wildcard matches every report folder, and definition/** matches pages, visuals, and bookmarks at any depth. The last option targets definition.pbir, a file you've banned from editing.

5. After /compact, Claude seems to have forgotten your TMDL conventions. Why?

After /compact, only the project-root CLAUDE.md is re-read right away. Path rules come back the next time Claude opens a matching file.

6. Which of these belongs in a TMDL path-scoped rule rather than in CLAUDE.md?

Only the first is about one file type. The other three apply to every file Claude might touch, so they stay always-on in CLAUDE.md.

7. Your team has a 10-step "add a new report page" procedure that you run now and then. Best home?

A procedure goes in a skill (Lesson 4). A PBIR rule would load that whole procedure every time Claude merely reads a visual.
