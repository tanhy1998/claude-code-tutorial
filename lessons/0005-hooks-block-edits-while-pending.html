Lesson 5 · From context to conditional enforcement

Hooks I: block model edits while Desktop has pending changes

A deny rule can say "never this file". A hook runs your own script before every tool call, so it can say "not now, because of that file".

~50 minHands-on: terminal + editor + Power BI DesktopPrimary source: Automate actions with hooks
Why this, now When you click Apply later in Power Query, Desktop saves the pending queries to .pbi\unappliedChanges.json. Microsoft's docs warn that if you then edit queries outside Desktop, your changes are lost and replaced by the queries in unappliedChanges.json when those changes are applied. The file is also saved in Git by default, so a teammate can pull it in with a branch.Semantic model folder: .pbi\unappliedChanges.json and External editing: limitations (Microsoft Learn). Right now two things guard against this: a CLAUDE.md line, which Claude chooses to follow, and step 1 of /add-measure, which only runs when the skill does. Neither one is enforcement. Today you add enforcement.

Your win today: a hand-written, committed PreToolUse hook. Whenever unappliedChanges.json exists, it blocks every TMDL edit, whether Claude uses Edit, Write, or PowerShell. You'll also break it on purpose and watch it fail open, so you know what to test after every change to it.

Part A: Where a hook sits

A hook is a command that Claude Code runs at a fixed point in its lifecycle. The docs call this deterministic control: certain actions always happen rather than relying on the LLM to choose to run them.Hooks guide, first paragraph. There are many events (SessionStart, Stop, FileChanged…). This lesson uses only PreToolUse. Lesson 6 adds PostToolUse. A PreToolUse hook runs after Claude has decided on a tool call and before that call runs:

Claude decides: Edit(_Measure.tmdl) │ ├─ PreToolUse hooks your script gets the call as JSON on stdin │ exit 2 → blocked. Your stderr goes to Claude as the reason │ exit 0 → no opinion; carry on │ ├─ permission rules deny → ask → allow (Lesson 3) ├─ permission mode auto / manual / bypass … │ ├─ the tool runs └─ PostToolUse hooks (Lesson 6: check what was written)

Two facts follow from that order, and both were confirmed in my tests:

  • A hook block beats every mode. A hook that returns permissionDecision: "deny" blocks the tool even in bypassPermissions mode. I ran Write and PowerShell edits in bypass mode with a pending file, and both were blocked.
  • A hook can't loosen your rules. Hooks can tighten restrictions but not loosen them past what permission rules allow. A hook returning "allow" doesn't bypass deny rules from settings.Hooks and permission modes. Your Lesson 3 deny list stays in charge.
LayerWhat decidesCan it check "does another file exist right now?"
CLAUDE.md lineThe model, if it remembersOnly if Claude decides to look
/add-measure step 1The model, only when the skill runsYes, but only inside that skill
Deny ruleClaude Code: tool + path patternNo. A rule matches the call itself, not the state of the disk
PreToolUse hookYour script, on every matching callYes. It's code, so it can check anything

Keep the CLAUDE.md line. It tells Claude why, so Claude asks you to apply the changes instead of hitting the wall over and over. The hook is the wall.

Part B: Anatomy

The config: in .claude\settings.json, next to permissions

lab\.claude\settings.json (the new part)"hooks": {
  "PreToolUse": [                                   ← the event
    {
      "matcher": "Edit|Write|PowerShell|Bash",      ← which tools (exact names, | = or)
      "hooks": [
        {
          "type": "command",
          "command": "powershell.exe",              ← exec form: a real .exe …
          "args": ["-NoProfile", "-ExecutionPolicy", "Bypass", "-File",
                   "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-unapplied.ps1"],
                                                    ← … plus its arguments, no shell in between
          "onFailure": "block"                      ← if the script crashes, block (fail closed)
        }
      ]
    }
  ]
}

Matchers are case-sensitive tool names. PowerShell has to be in the list. On Windows, Claude treats PowerShell as the primary shell and routes shell commands through it, and a hook that matches only Bash never fires there.Hooks reference: PowerShell tool input. ${CLAUDE_PROJECT_DIR} is the project root where the session started, here lab\.

What your script receives on stdin

{ "tool_name": "Edit",
  "tool_input": { "file_path": "C:\\…\\lab\\Contoso.SemanticModel\\definition\\tables\\_Measure.tmdl",
                  "old_string": "…", "new_string": "…" }, … }

{ "tool_name": "PowerShell",
  "tool_input": { "command": "Add-Content Contoso.SemanticModel\\definition\\…", … }, … }

Edit and Write give you a file_path (absolute). PowerShell and Bash only give you command, the raw text. So the script can't know for sure which files a shell command will touch. It can only search the text.

What your exit code means (PreToolUse)

ExitTool callWho sees what
0Continues through the normal permission flowClaude never sees stderr from a hook that exits 0
2BlockedYour stderr goes to Claude as the reason
anything elseContinues. It's a non-blocking errorA hook error notice with the first line of stderr

Read that last row twice. Exit code 1 without valid JSON output is a non-blocking error… If your hook is meant to enforce a policy, use exit 2. A guard that crashes fails open. "onFailure": "block" (v2.1.295+) flips that: a PreToolUse failure blocks the tool call.Exit code output and Block the action when a hook fails. There's also a JSON way to answer (permissionDecision: allow / deny / ask). Today you only need exit 2.

Part C: Three Windows traps (tested on v2.1.302)

What I found running these hooks with Windows PowerShell 5.1
  1. PowerShell errors don't stop the script by default. In my first draft, ConvertFrom-Json failed on bad input. The script kept going with an empty $call and exited 0, so the edit was allowed. The fix: start the script with $ErrorActionPreference = "Stop". Then any error exits 1, and onFailure: "block" turns that into a block. I tested both: with onFailure, a crashing script blocked the Edit. Without it, the Edit went through and Claude saw no notice.
  2. Use exec form (command + args), not shell form. With "shell": "powershell" and & "…\script.ps1", my script's exit 2 reached Claude Code as status 1. It only blocked because onFailure was set. Exec form with -File passed 2 through cleanly. This is also the Windows example in the docs.
  3. A typo in the -File path fails open, even with onFailure: "block". powershell.exe starts, prints The argument … to the -File parameter does not exist, and the debug log shows finished with status 0. Claude Code never sees a failure. The only way to catch this is to test the block after every edit to the hook config. You'll do that in step 7.

Also: keep the .ps1 plain ASCII. Windows PowerShell 5.1 reads a BOM-less script in the system ANSI code page, so curly quotes or em dashes can break it.about_Character_Encoding. That's the opposite of what PBIP files need: UTF-8 without BOM.

Part E: Retrieval practice

Scroll up only after you've answered.

1. Why can't a deny rule do today's job?

Edit(**/*.tmdl) would block TMDL edits always. "Only while unappliedChanges.json exists" depends on the state of the disk, and only code can check that.

2. Your hook script hits an error and exits 1. onFailure isn't set. What happens to the Edit?

Only 2 blocks. A guard that crashes fails open unless you set "onFailure": "block". In my test the edit went through and Claude saw no notice.

3. The matcher is "Edit|Write". Claude uses the PowerShell tool to run Set-Content on _Measure.tmdl. What happens?

Matchers are exact tool names. On Windows, shell commands go through the PowerShell tool, so it has to be listed. Even then, the script only sees command text, so treat shell coverage as best effort.

4. The -File path in args has a typo, and onFailure is "block". The pending file exists. Claude edits a TMDL file. What happens?

That was step 7. powershell.exe itself started, so as far as Claude Code knew, the hook ran and reported 0. onFailure only catches failures that Claude Code can see. The protection here is testing the block after every change.

5. A hook returns permissionDecision: "allow" for an Edit on definition.pbir, which your settings deny. What happens?

A hook returning "allow" doesn't bypass deny rules from settings. The reverse does work: a hook's block beats every allow rule and every mode.

6. A teammate runs claude --permission-mode bypassPermissions. The pending file exists, and Claude edits TMDL. What happens?

That's the docs' point about enforcing policy that users can't bypass by changing their permission mode. I ran it in bypass mode, and both Write and PowerShell were blocked.

7. The pending file exists. You run /add-measure, whose !`Select-String … _Measure.tmdl` line mentions .tmdl. What happens?

I tested this: a skill's !`…` line read a .tmdl while the file was pending, and the hook never ran. That's what you want. The skill can still see the pending state and stop politely at step 1, and the hook catches any edit that gets past it.

8. Where must the hook put its reason for a block?

With exit 2, the message that comes with the block is your hook's stderr. Stdout with exit 0 is for the JSON form, or it goes to the debug log.

Write it out: the whole "hooks" block for settings.json, from memory. Then say in one sentence why the CLAUDE.md line about unappliedChanges.json should stay now that the hook exists.

"hooks": {
  "PreToolUse": [
    { "matcher": "Edit|Write|PowerShell|Bash",
      "hooks": [
        { "type": "command",
          "command": "powershell.exe",
          "args": ["-NoProfile", "-ExecutionPolicy", "Bypass", "-File",

The hook only says "no". The CLAUDE.md line tells Claude why, so it checks first and asks you to apply the changes, instead of planning an edit and hitting the block.
